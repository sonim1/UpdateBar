# UpdateBar 화면별 E2E·UX·접근성 감사

검토 기준은 v0.6.30, 커밋 `3918ae8b5d64d303bf3721bd84b0fddd94bd9ae9`이다. 실제 macOS 앱, 터미널 TUI, CLI, 공개 웹사이트를 각각 실행했다. 구현 범위는 재현한 오류와 사용자가 동작을 이해하거나 키보드로 접근하는 데 필요한 개선이다.

## 1. 판단과 우선순위

가장 먼저 고칠 문제는 설정 화면 진입과 문자 입력이다. 정상 설정이 화면에 표시되지 않거나 도구 이름 입력이 종료 명령으로 처리되면, 사용자에게 기능 자체가 작동하지 않는 것으로 보인다. 그다음은 숫자의 의미, 접근성 이름, 창 위치처럼 모든 작업의 이해와 이동을 돕는 문제다. 화면 재설계보다 이러한 동작의 일관성이 먼저다.

| 우선순위 | 확인한 문제 | 영향 | 적용한 해결 |
| --- | --- | --- | --- |
| 높음 | Settings를 사이드바로 처음 열면 기본값이 표시됨 | 저장된 `24h / 1` 대신 `6h / 3`; Save는 내부 설정이 없어 아무 동작도 하지 않음 | 화면 진입 생명주기에서 설정 로드. 미저장 수정이 없으면 재진입에서 외부 변경 반영 |
| 높음 | TUI Prompts의 `m`, `q`가 전역 단축키에 가로채임 | `npm`, `gemini` 입력 중 메뉴로 돌아가고 `jq` 입력 중 종료 | 문자 입력 화면을 먼저 처리. Escape로 메뉴 복귀, Ctrl+C로 종료 |
| 중간 | Dashboard를 다시 열 때마다 중앙 정렬 | 사용자가 배치한 창이 다른 위치로 이동 | 생성 시 한 번만 중앙 정렬 |
| 중간 | Overview 지표와 Scan 요약에 보이는 이름이 없음 | 숫자·아이콘만으로 업데이트/승인/조회 시각·발견/활성/비활성을 구별해야 함 | 기존 의미 이름을 화면에도 표시; 도움말과 접근성 값 유지 |
| 중간 | Scan 결과 표의 접근성 이름 없음 | 여러 표 사이에서 결과 영역을 구별하기 어려움 | `Installed tool scan results` 컨테이너 이름 추가 |
| 낮음 | 웹 첫 키보드 포커스에서 본문으로 바로 이동할 링크 없음 | 반복되는 헤더·탐색을 순서대로 통과해야 함 | 네 경로의 첫 링크에서 본문으로 포커스 이동 |
| 코드 정리 | 열리지 않는 이전 팝오버 화면 객체를 모델 전달용으로 생성 | 상태 갱신에 불필요한 SwiftUI 호스팅 화면과 NSPopover가 생성됨 | 앱 진입부가 기존 모델을 직접 보유·갱신 |

설정 오류를 분석하던 초기의 “Save가 기본값으로 덮어쓸 수 있다”는 추정은 철회했다. 실제 Save의 `loadedConfig` 검사 때문에 저장하지 않는다. 이 문서는 코드 경로와 재현 결과를 기준으로 한다.

## 2. 시험 환경과 증거

- 실제 앱 패키지를 별도 작업 트리에서 빌드하고, 테스트용 HOME·CFFIXED_USER_HOME·UPDATEBAR_HOME을 자식 프로세스에만 설정했다.
- 정상, 업데이트 필요, 승인 필요, 고정, 비활성, 검사 실패, 긴 이름을 포함한 8개 합성 도구를 사용했다. 업데이트 명령은 시험 디렉터리의 버전 파일만 바꾼다.
- 브라우저는 작업용 Chrome 프로필로 실행했다. 기존 사용자의 탭·쿠키·클립보드 내용은 시험 데이터로 읽지 않았다.
- TUI는 실제 PTY에서 CLI를 호출했다. 출력 필터가 TTY를 제거하는 문제는 시험 하네스에서 해결했다.
- 운영 사이트의 네 경로를 375/768/1280px에서 먼저 확인하고, 변경 후 로컬 배포와 같은 정적 파일을 다시 확인했다.
- 로그·AX 트리·PNG·PTY 기록은 로컬 `.omo/evidence/e2e-ux-20261013/`에 보존한다. 이 경로는 Git에서 제외되며 공개 배포에 포함되지 않는다.

### 기능·안전 경계

Items의 업데이트 가능 항목과 Needs review 항목을 섞지 않는다. 선택 업데이트, 검색 범위 업데이트, 실패 재시도는 각각 대상이 다르다. 승인 화면은 정확한 명령 필드를 검토하는 단계이며, 승인 자체가 업데이트 실행을 의미하지 않는다. Stop은 실행 중인 작업을 강제로 죽이는 기능이 아니라 현재 작업 이후의 중단 경계다.

Scan의 체크 해제는 등록 항목 삭제가 아니라 비활성화다. 신규 발견 결과, 등록된 상태, 검사 오류가 각각 다르게 표현되어야 한다. 부분 실패·실패 후 재시도·화면 전환 뒤 늦게 도착한 결과는 기존 회귀 검사로 보호한다.

### 화면 이동과 크기

같은 Dashboard 창을 유지하는 구조에서는 재열기가 사용자의 위치를 바꾸지 않아야 한다. Settings의 데이터 준비도 어느 메뉴로 진입했는지에 의존하면 안 된다. 최초 진입과 수정 없는 재진입은 저장값을 로드하고, 미저장 수정이 있으면 사이드바 이동 중 입력을 유지한다. 메뉴의 명시적인 재열기는 이미 보이는 Settings도 reload한다. 이 마지막 경로와 미저장 입력 보존은 최초 개선에서 빠졌지만 실제 화면·회귀 검사로 재현해 보완했다. 저장과 재진입은 같은 pendingChanges 계산을 사용한다.

Overview 지표는 기존 시스템 글꼴·색·간격·모서리를 그대로 사용한다. 새 이름은 이미 접근성 모델에 존재하는 의미를 재사용하므로 화면과 보조 기술의 용어가 갈라지지 않는다. Scan도 같은 원칙을 적용한다.

새 이름은 필수 정보를 전달하므로 기본 텍스트색을 사용하고 작은 글꼴로 계층을 구분한다. Light 캡처에서 secondary 지표 설명의 대표 픽셀은 `#7a7a7a` / `#f3f3f3`, Scan 설명은 `#808080` / `#ffffff`였다. 작은 텍스트 대비의 [W3C 4.5:1 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)을 읽기 품질의 벤치마크로 삼아 시스템 primary/labelColor로 보완했다. 픽셀 표본은 렌더링 관찰값이며 전체 네이티브 앱의 WCAG 적합성 인증이 아니다.

## 4. TUI 화면별 분석

| 화면/상태 | 특징 | E2E·사용성 판단 |
| --- | --- | --- |
| 메뉴 | 방향키로 작업 선택, Enter 실행 | 선택 표시와 요약이 분리되어 있으며 마우스 없이 이동 가능. 외부 변경은 Refresh Status 또는 새 작업의 상태 조회 때 반영 |
| Status | 도구별 상태·버전·오류를 텍스트로 표시 | 색만 사용하지 않는다. 긴 이름과 오류는 터미널 폭에 맞춰 줄바꿈 |
| Scan & Add | 발견 목록을 키보드로 선택하고 등록 | full 후보만 등록 가능. check-only/수동 후보를 실행 가능한 것으로 오해하지 않도록 capability 표시 유지 |
| Check Now | CLI 검사를 수행하고 상태를 갱신 | 명령 실패 시 이전 성공 상태를 최신 결과처럼 표시하지 않는 기존 검사 유지 |
| Update selection | outdated 항목에서 실행 범위 선택 | 승인/비활성/고정 항목을 전체 업데이트 범위에 넣지 않음 |
| Confirmation | 선택 수를 다시 보여 주고 Enter 실행, Escape 취소 | 실행 전 의도 확인이 존재하며 취소 시 업데이트하지 않음 |
| Progress / Cancel | CLI 이벤트를 표시하고 c/q로 취소 요청 | 실행 중의 취소 키와 입력 화면의 문자 키는 별도 책임이어야 함 |
| Logs | 현재 TUI 세션의 최근 12줄 | macOS의 영속 이력 화면과 다르다. 과거 전체 이력을 기대하면 CLI history 사용 필요 |
| Config Path | 실제 UPDATEBAR_HOME 기반 설정 파일 위치 | 편집 화면이 아니다. 긴 경로는 줄바꿈되지만 실제 경로 값은 보존 |
| Prompts | 도구 이름 + npm/Homebrew/GitHub 레시피 템플릿 | 전역 m/q 처리 오류 수정. 문자 입력 중에는 Escape만 메뉴 이동; 일반 화면과 실행 중 취소 동작은 유지 |

문자 입력 회귀는 입력 문자열 전체를 한 번에 전달하는 기존 테스트가 놓쳤다. 실제 사용자처럼 한 글자씩 `npm`, `jq`, `gemini`를 전달하고 출력 이벤트를 기다리는 검사를 추가했다. 고정 sleep 대신 렌더 출력 이벤트와 실패 시한을 사용한다.

| `/404.html` | 잘못된 경로에서 복구 | 본문 landmark·헤딩·복귀 링크 확인. 같은 건너뛰기 규칙 적용 |

수정 전 12개 반응형 사례에서 가로 넘침·alt 속성 누락·깨진 이미지가 없었고, 각 경로에 main과 h1이 하나씩 있었다. 홈/macOS의 설치 설명은 모달이 아닌 native details다. 복사 성공 피드백과 FAQ 펼침을 실제 브라우저로 확인했다.

건너뛰기 링크는 main landmark가 없어서 추가한 것이 아니다. 명시적인 키보드 이동 경로를 보강하는 개선이다. 숨겨진 링크는 Tab을 받으면 보이고 Enter 이후 본문에 실제 포커스가 놓인다. 이미지 reel의 일시정지·reduced motion, 설치 프롬프트의 클립보드 실패 시 수동 선택 경로도 구분해 검증한다. 클립보드 차단은 브라우저 API 실패를 주입한 시험이며 실제 운영 장애라고 기록하지 않는다.

CSS 변경 시 네 HTML 경로의 SHA-256 캐시 키를 함께 갱신했다. 새 HTML과 이전 CSS가 섞이는 배포 회귀를 방지한다.

## 6. 통합 개선 방향과 코드 판단

1. **진입·범위·결과의 일관성부터 유지한다.** 화면이 필요한 데이터를 자신이 로드하고, 실행 버튼은 현재 선택/검색 범위를 설명하며, 결과는 검사·업데이트·승인을 구별해야 한다. 이번 설정·입력·지표 수정이 여기에 해당한다.
2. **웹 → 설치 → 발견 → 검토 → 업데이트를 연결한다.** 각 화면은 서로 다른 단계를 맡는다. 현재 경계와 안전한 명령 검토를 유지하는 편이 모든 화면에 같은 기능을 중복 구현하는 것보다 낫다.
3. **접근성 의미와 보이는 의미를 같은 데이터에서 만든다.** 기존 모델의 지표 이름을 재사용했다. 컨테이너 이름, 키보드 포커스, 색 외 상태 문구를 우선한다.
4. **후속 후보는 실제 이용 문제로 순서를 정한다.** Logs 검색·기간 필터와 TUI의 영속 이력 안내가 우선 후보다. Scan의 빈 화면 시작 안내와 용어 설명도 온보딩 시험에서 평가할 만하다. 전체 UI 교체·신규 분석 SDK·상태 관리 프레임워크 도입의 근거는 이번 감사에서 나오지 않았다.

코드 정리는 동작 경계에 한정했다. 외부 진입점에 묶인 Settings prepare 경로를 제거하고, TUI 문자 입력 우선순위를 정리하고, 앱 진입부에서 이전 팝오버 화면 대신 모델만 사용한다. CLI/core/UI 경계, JSON 출력 계약, 승인 검증, 취소·세대 검사는 유지한다. 큰 파일이라는 이유만으로 Scan 비동기 상태나 TUI 전체를 분할하지 않는다.

레거시 팝오버 구현과 독립 테스트의 전체 폐기는 이번에 포함하지 않았다. 현재 앱의 생성 경로를 제거한 뒤에도 해당 테스트와 재사용 모델은 남는다. 삭제하려면 별도 마이그레이션으로 테스트의 보호 범위를 현행 화면으로 옮겨야 한다.

요약 값의 출처도 구분해야 한다. macOS는 외부 파일 변경을 감시하지만 TUI 메뉴는 최근 조회한 스냅샷을 표시한다. 작업 진행은 해당 프로세스의 세션 상태이며 Logs·30일 차트는 공유된 영속 이력이다. 검사 이력의 “발견한 새 버전 수”와 현재 실행 가능한 업데이트 수가 승인 상태 때문에 다를 수 있다. 후속 개선에서는 이러한 문구를 더 명확히 하는 편이 낫다. TUI 취소 메시지가 적색 오류 영역에 남는 표현도 중립적인 안내로 개선할 후보다.

`UPDATEBAR_BIN`이 CLI 자식 환경에 다시 전달되지 않는다는 후보는 버그가 아니었다. 먼저 그 값으로 실행 파일을 해석한 뒤 정확한 절대 경로를 spawn한다. 환경 허용 목록을 불필요하게 넓히지 않았다.

## 7. 검증 상태와 제한

수정 전 전체 품질 검사는 통과했고, 새 회귀 검사는 수정 전 실패를 확인했다. 최종 변경의 전체 품질 검사는 **EXIT 0**이다. Swift **977개**, TUI **143개**가 통과했다. Swift format, TypeScript typecheck, ESLint, 셸·설치·릴리즈 계약 검사, 실제 CLI/TUI 입력 검사, 앱 패키징과 네이티브 smoke 검사도 완료했다. 중간 실행에서 발견한 Scan 접근성 값 중복은 별도 캡션으로 해결했으며, 숫자 leaf의 기존 접근성 값 검사는 유지했다.

| 실제 동작 | 결과와 증거 |
| --- | --- |

개발 도구 업데이트는 모두 시험 디렉터리의 합성 버전 파일에 한정했다. intentionally failing 검사 항목 때문에 CLI status의 exit 10은 예상한 attention 계약이며 검사 실패를 숨긴 결과가 아니다. Homebrew/npm 인터페이스는 시험용 실행 파일로 제한했다.

VoiceOver 음성 출력을 직접 청취하는 시험은 수행하지 않았다. 접근성 트리·레이블·값·키보드 동작 검사는 화면 읽기 프로그램 전체 인증을 대신하지 않는다. Native light는 테스트 프로세스의 appearance 인수로 실행했으며 사용자의 시스템 테마를 바꾸지 않았다. 실행 중 OS 테마 전환은 별도 시험하지 않았다. Native Templates의 프롬프트 입력·미리보기는 직접 확인했고 복사 로직은 자동 검사로 확인했으며, 실제 시스템 클립보드 버튼은 사용자의 클립보드를 보존하기 위해 누르지 않았다. 접근성 점수나 Lighthouse 점수를 측정한 것처럼 제시하지 않는다. 지원 메일 전송, 약관 수락, 실제 개발 도구 업데이트는 이 QA의 목적이 아니다.

최종 코드 리뷰·PR 검증 결과는 Git 기록과 PR 체크에서 확인한다. 이 감사의 수동 증거와 전체 로컬 검사는 위 경로에 보존한다.
